# Validation And Diagnostics

Polygen validates grammars in stages.

In the TypeScript rewrite, those stages are still visible through the public API and error types:

- tokenization
- parsing
- compilation and semantic validation
- generation

## Error Types

### `TokenizerError`

Tokenizer errors happen before parsing, when the source text cannot be turned into valid tokens.

Typical causes:

- unterminated comments
- malformed quoted strings
- invalid escape sequences
- characters that do not belong to any recognized token

Example areas to inspect:

```text
S ::= "unterminated;
S ::= "bad \q escape";
(* comment never closes
```

### `ParserError`

Parser errors happen when the token stream is valid in isolation, but the grammar structure is not.

Typical causes:

- missing `;`
- malformed grouping delimiters
- misplaced operators
- declaration heads that do not match the grammar structure

```text
S ::= "hello"
```

The tokenizer can understand that input, but the parser rejects it because the declaration is incomplete.

### `CompileError`

Compile errors happen after parsing, once Polygen validates semantic relationships inside the grammar.

Current hard-error cases in the TypeScript port include:

- undefined non-terminals in strict mode
- duplicate declarations in the same scope
- cyclic unfold chains
- malformed explicit label selections when the compiler can determine that statically
- unsupported import declarations during compilation
- unsupported multi-segment non-terminal paths during compilation

Examples:

```text
S ::= Missing;
```

```text
S ::= one;
S ::= two;
```

```text
S ::= >S;
```

### `GenerationError`

Generation errors happen after successful compilation, while producing output.

Current runtime-error cases include:

- missing start symbol
- invalid `maxExpansions`
- recursion budget exhaustion

```ts
import { polygen } from "polygen";

const text = polygen(grammar, {
  start: "Missing",
  maxExpansions: 100
});
```

## Current Warning Surface

Warnings are available through:

- `polygenWithInfo(...)`
- `polygenSegmentWithInfo(...)`
- `compileGrammarWithInfo(...)`

Each warning currently carries:

- a machine-readable code
- a human-readable message
- a source range
- severity `warning`

### Warning Codes Emitted Today

#### `invalid-label-selection-fallback`

Emitted only in compatibility mode when an invalid explicit label selection is ignored instead of raising `CompileError`.

#### `undefined-nonterminal-fallback`

Emitted only in compatibility mode when an undefined non-terminal in atom position is treated as terminal text instead of raising `CompileError`.

#### `useless-unfold`

Emitted when unfolding a group with only one alternative.

This matches the spirit of the historical useless-unfolding warning.

#### `unfold-assign`

Emitted when unfolding an assignment-bound symbol.

This matches the historical warning about unfolding a suspended symbol: the construct is legal, but conceptually surprising enough to deserve attention.

## Compatibility Mode Diagnostics

Strict mode is the default.

If you opt into:

```ts
compilePolicy: {
  preset: "compat";
}
```

two compile-time failures can currently become warnings with fallback behavior:

- undefined simple non-terminals in atom position may become terminal text
- invalid explicit label selection may be ignored

Compatibility mode does not relax:

- tokenizer syntax
- parser structure
- declaration heads
- duplicate declarations
- cyclic unfolding
- runtime option validation

## Historical Checker Parity Gaps

The historical OCaml project went further in several areas than the current TypeScript port.

### Not Yet Implemented In The TypeScript Checker

- full static detection of non-terminating recursive grammars
- epsilon-only grammar rejection
- potential-epsilon warnings
- destructive-selection warnings
- useless-permutation warnings
- the historical warning-level hierarchy
- the `I` symbol convention used by the old `-info` flow

These omissions matter because the TypeScript port can currently accept some grammars that the historical checker would have rejected or warned about, then rely on runtime safeguards instead.

## Practical Debugging Workflow

When a grammar behaves unexpectedly, the most useful sequence is:

1. call `tokenize(...)` if you suspect lexical issues
2. call `parseGrammar(...)` if the structure itself might be wrong
3. call `compileGrammarWithInfo(...)` to inspect warnings without generating text yet
4. call `polygenWithInfo(...)` with a fixed seed so the run is reproducible

Example:

```ts
import { compileGrammarWithInfo, parseGrammar, polygenWithInfo } from "polygen";

const parsed = parseGrammar(grammar);
const compilation = compileGrammarWithInfo(parsed);
const run = polygenWithInfo(grammar, { seed: 42 });
```

This lets you separate syntax problems, semantic problems, warnings, and runtime generation behavior.
