# Translation And Preprocessing

The historical Polygen appendix described a sequence of translation rules from concrete syntax into the simpler runtime language.

The TypeScript rewrite performs the same broad kind of work, but the implementation is split between parsing and compilation.

This page documents the current behavior in implementation order.

## Phase 1: Tokenization

The tokenizer:

- removes trivia such as spaces, tabs, newlines, and comments
- preserves source positions for diagnostics
- decodes quoted-string escapes
- classifies identifiers into terminals, non-terminals, and label tokens

Comments are gone by the time parsing starts.

## Phase 2: Parser-Level Sugar Expansion

Some translation happens immediately while parsing.

### Weighted Production Expansion

When the parser sees weighted alternatives, it expands them into repeated entries relative to the lowest modifier in the same series.

```text
S ::= +good | bad | --worse;
```

This is expanded internally by duplicating alternatives so the generator can still choose uniformly from a flat array later.

### Weighted Multi-Selection Labels

The same relative-weighting expansion rule is used for label lists inside `.(...)`.

```text
S ::= Greeting.(+formal|--casual|plain);
```

By the end of parsing, the label list is already expanded to the weighted equivalent.

## Phase 3: Deep-Unfold Normalization

Before ordinary compilation of a `>> ... <<` group, the compiler recursively rewrites its contents so that nested groups and non-terminals become unfolded targets unless they are explicitly locked.

That is why deep-unfold behaves like a recursive shorthand for many local unfold operations.

## Phase 4: Scope Validation

Compilation validates declaration structure before generation-ready objects are produced.

Current checks include:

- duplicate declarations in the same scope
- cyclic unfold chains
- static label-availability checks where the compiler can determine them

Some historical OCaml checks still remain outside the current rewrite, especially the broader static recursion and epsilon analyses.

## Phase 5: Positional Variant Expansion

A sequence is represented as a list of positions, where each position may contain:

- one atom, or
- several comma-separated alternatives that must stay aligned with other positions of the same width

Example:

```text
S ::= he,she is a handsome,pretty act ^ or,ress;
```

The compiler turns this into several aligned positional variants.

If comma-separated positions in the same sequence do not all have the same width, compilation fails.

## Phase 6: Atom Compilation

Each atom is compiled according to its semantics.

### Ordinary Groups

`( ... )` becomes a compiled subgrammar.

### Optional Groups

`[ ... ]` becomes a choice between:

- epsilon
- the compiled subgrammar body

### Mobile Groups

`{ ... }` becomes a compiled subgrammar marked as mobile so it can be permuted with other mobile atoms in the same sequence.

### Repetition Groups

`( ... )+` becomes a repeat node that generates the grouped body at least once, then repeats it while the runtime keeps drawing continuation.

### Unfolded Groups And Non-Terminals

`>` lifts each alternative of the target into the surrounding compiled series instead of leaving the target as one grouped block.

### Locked Targets

`<` prevents the target from being flattened by the surrounding unfold behavior.

## Phase 7: Combination And Permutation

After atoms are compiled, the compiler combines the possible placements.

Then it permutes only the atoms marked as mobile, and only within the sequence they belong to.

This is why permutation is sequence-local rather than global.

## Phase 8: Runtime Generation

Generation then works from the compiled model.

At runtime it still has to decide:

- which alternative to choose from a compiled production
- which label to pick from a multi-selection set
- whether an optional branch survives or collapses to epsilon
- how many times a repeat node keeps iterating

Weak bindings regenerate each time. Strong bindings memoize after first realization within the current run.

## Concrete Consequences

### Why Grouping Changes Probability

Grouping delays some choices until after outer choices are made.

### Why Unfold Changes Probability

Unfold lifts inner alternatives outward so they share the outer choice level.

### Why Positional Generation Is Strict About Width

The compiler pairs the first comma-separated atom with the first atom in every other same-width position, then the second with the second, and so on.

### Why Deep-Unfold Needs Lock

Without lock, recursive flattening would sometimes unfold more than you want. Lock keeps selected atoms grouped or referenced.

## Current Rewrite Boundary

This page documents the current implementation behavior, not a byte-for-byte restatement of the original OCaml appendix.

The main remaining gap is that the rewrite still lacks a fully formal spec-style translation document matching the historical appendix line for line.

What it now does provide is:

- the real current implementation order
- the real current runtime consequences
- the key parity differences that matter to grammar authors
