# Syntax Reference

This page is the rewrite-native replacement for the historical appendix sections on concrete syntax, abstract syntax, lexical rules, and escape sequences.

It describes the current TypeScript implementation, including intentional divergences from the older ASCII-oriented lexer.

## Concrete Syntax

The following EBNF-style sketch matches the current parser closely.

```ebnf
Grammar        ::= Declaration (";" Declaration)+

Declaration    ::= Nonterminal "::=" Production
                 | Nonterminal ":=" Production
                 | "import" QuotedPath "as" Nonterminal

Production     ::= ModifiedSequence ("|" ModifiedSequence)*
ModifiedSequence ::= ("+" | "-")* Sequence

Sequence       ::= [Label ":"] Position+
Position       ::= Atom ("," Atom)*

Atom           ::= Term
                 | "^"
                 | "_"
                 | "\\"
                 | Unfoldable
                 | ">" Unfoldable
                 | "<" Unfoldable
                 | Atom "."
                 | Atom DotLabel
                 | Atom ".(" Labels ")"

Labels         ::= ModifiedLabel ("|" ModifiedLabel)*
ModifiedLabel  ::= ("+" | "-")* Label

Unfoldable     ::= NonterminalPath
                 | "(" Sub ")" ["+"]
                 | "[" Sub "]"
                 | "{" Sub "}"
                 | ">>" Sub "<<"

Sub            ::= (Declaration ";")* Production
NonterminalPath ::= Nonterminal ("/" Nonterminal)*
```

### Notes On Current Support

- `import "..." as Name` is parsed, but compilation still rejects import declarations.
- multi-segment non-terminal paths such as `Pkg/Name` are parsed, but compilation currently rejects imported or nested paths.
- `( ... )+` means one-or-more repetition of a grouped subgrammar.
- `.(...)` multi-selection labels support weighting with `+` and `-`.

## Abstract Syntax Shape

The public TypeScript package exposes the parser AST types. At a high level, the tree looks like this:

| Node                | Meaning                                                                    |
| ------------------- | -------------------------------------------------------------------------- |
| `Grammar`           | Root node containing top-level declarations                                |
| `Declaration`       | Either a binding declaration or an import declaration                      |
| `BindDeclaration`   | A `::=` or `:=` declaration                                                |
| `ImportDeclaration` | A parsed import declaration                                                |
| `Production`        | A list of alternative sequences                                            |
| `Sequence`          | One production alternative, optionally labeled                             |
| `Atom`              | A terminal, non-terminal, group, select, multiselect, unfold, or lock node |

### Group Modes

The parser normalizes grouped syntax into `GroupAtom` nodes with one of these modes:

| Group mode           | Source form |
| -------------------- | ----------- |
| `std`                | `( ... )`   |
| `optional`           | `[ ... ]`   |
| `mob`                | `{ ... }`   |
| `deep-unfold`        | `>> ... <<` |
| `repeat-one-or-more` | `( ... )+`  |

### Terminal Special Values

Some operators are represented as special terminal values in the AST and compiled model:

| Value        | Source form |
| ------------ | ----------- |
| `concat`     | `^`         |
| `epsilon`    | `_`         |
| `capitalize` | `\\`        |

This is why concat, epsilon, and capitalization travel through parsing and compilation as terminal-like atoms even though they are operational markers.

## Lexical Rules

The TypeScript rewrite intentionally broadens the historical lexer.

### Bare Terminals

A bare terminal may start with:

- a Unicode lowercase letter
- a Unicode modifier or uncased letter class accepted by the current tokenizer
- a digit
- an apostrophe

It may continue with:

- Unicode letters
- combining marks
- digits
- apostrophes

Examples:

```text
hello
niño
東京
'tis
adventuringgear
```

### Bare Non-Terminals

A bare non-terminal must start with a Unicode uppercase or titlecase character under the current tokenizer rules.

It may continue with:

- Unicode letters
- combining marks
- digits
- apostrophes

Examples:

```text
S
Greeting
Épée
Tokyo2
```

### Labels

Labels may contain:

- Unicode letters
- combining marks
- digits
- underscores

Dot-label syntax such as `.formal` cannot start with `_`.

### Reserved Bare Keywords

These bare words are tokenized specially when they appear in terminal position:

- `import`
- `as`

If you want them emitted literally, quote them.

```text
S ::= "import" | "as";
```

### Structural Tokens

The current tokenizer recognizes these operators and delimiters:

| Token    | Meaning                             |
| -------- | ----------------------------------- | ----------- |
| `;`      | declaration terminator              |
| `:`      | label separator                     |
| `(` `)`  | group delimiters                    |
| `[` `]`  | optional group delimiters           |
| `{` `}`  | mobile group delimiters             |
| `::=`    | weak binding                        |
| `:=`     | strong binding                      |
| `        | `                                   | alternation |
| `>`      | unfold                              |
| `>>`     | deep-unfold open                    |
| `<`      | lock                                |
| `<<`     | deep-unfold close                   |
| `+` `-`  | weighting                           |
| `^`      | concat                              |
| `_`      | epsilon                             |
| `.`      | selection reset                     |
| `.label` | explicit selection                  |
| `,`      | positional generation separator     |
| `\\`     | capitalization                      |
| `/`      | non-terminal path segment separator |
| `.(`     | multi-selection open                |

### Comments And Whitespace

- spaces and tabs are ignored as separators
- newlines are ignored structurally but still update source positions
- comments use `(* ... *)`
- comments can nest

## Escape Sequences In Quoted Strings

The current tokenizer supports these escapes inside quoted terminals:

| Escape  | Meaning                |
| ------- | ---------------------- |
| `\\\\`  | backslash              |
| `\\"`   | quote                  |
| `\\n`   | newline                |
| `\\r`   | carriage return        |
| `\\b`   | backspace              |
| `\\t`   | tab                    |
| `\\123` | decimal character code |

### Important Note On Numeric Escapes

The historical materials have been inconsistent about whether three-digit escapes should be interpreted as octal or decimal.

The current TypeScript tokenizer interprets them as three-digit decimal character codes:

```ts
String.fromCharCode(Number.parseInt(lexeme, 10));
```

That is the actual behavior of the rewrite today.

## Relationship To The Historical Appendix

Compared with the historical HTML appendix:

- the rewrite keeps the same broad grammar model
- the lexer intentionally broadens accepted Unicode input
- import declarations and path syntax are parsed more generously than they are currently compiled
- the appendix here documents the current TypeScript behavior first, then points out compatibility gaps where they matter
